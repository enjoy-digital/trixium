# V0: measured 27B decode baseline, 2026-09-21

This is validation of profiling firmware **826f4ae** on the existing
`xcu1525_n16_150_v8` bitstream at 150 MHz. It is not a new bitstream release or a
datapath speedup. Later typed-trace commits are not the firmware measured here.

## Result

Three repetitions of `bench 8`, prompt IDs `[1, 2, 3]`, greedy generation:

| Measurement | Result |
| --- | --- |
| Median decode throughput, ready-to-ready wall time | **0.217073 tok/s** |
| Decode throughput across repetitions | 0.217072929–0.217073613 tok/s |
| Median time to first token | **13.628233 s** |
| Median prefill, including final prompt logits | 13.374538 s |
| Generated tokens / measured decode outputs per request | 8 / 7 |
| Forwards per request | 3 prefill + 7 decode = 10 |
| Actual allocated context capacity | **1,024 tokens** |
| Context occupancy at request end | 10 forwarded tokens |
| Historical mixed-request `BENCH` display | 0.174 tok/s (not decode-only) |

Generated IDs were `4 5 1 198 262 220 16 17` in all three repetitions. Console
emission contributes about 0.00010 s per request; excluding it barely changes
decode throughput. Each request takes about 45.875 s and exceeds 2^32 cycles.
The new 64-bit totals remain valid; legacy hardware overlap correctly reports
unavailable instead of percentages computed from wrapped counters.

The earlier 0.220 forwards/s candidate came from a different mixed `bench 2`
workload. It is not a decode-only rate to use for an apples-to-apples speedup.
16k/64k filled contexts, per-token p95, 256-output workloads and a one-hour soak
have **not** been qualified by this short baseline. Current allocated capacity
cannot support those long contexts.

## Implementation checks

115 selected tests passed: artifact/benchmark/trace/timing validation, C profiler
harnesses, atomic-counter RTL, layout, arithmetic, quantization, GGUF, embedding,
27B geometry, hybrid mirror, DeltaNet state, AXI shim and engine reset. Firmware
cross-builds passed for v8, FK33 v16b and the newly elaborated simulation CSR map
(including real generated 64-bit snapshot accessors). Existing unrelated compiler
warnings remain. No small-model board performance regression result is claimed.

The expanded regression run subsequently passed **131 tests in 228.94 s**
(`build/v0-final-regressions.log`); the extra tests cover the simulation validator.
Targeted tests also cover the later boot-boundary and archived-trace cases.

The full FPU SoC simulation completed all three boot legs with the new CSR map:
`GEN` and `GEN-HW` both gave `[143, 244]`; `GEN-SP` gave
`[143, 244, 270, 465, 29, 170]`. All match the Python reference. The speculative
counters were zero: this is a hybrid boot regression, not an MTP validation.
The real firmware printed valid `coherent64` overlap snapshots. The simulation
used `--cpu-type vexiiriscv --icache-kb 32 --vexii-extra='--with-rvf --with-rvZbb'`.
For a PTY-backed simulator, use `timeout --foreground`; ordinary `timeout` creates
a background process group that its console setup can stop. An earlier soft-float
attempt was stopped without a token result and is not counted as a pass.

The subsequent `dbg 3; gen 1 1 2 3` produced all 87 typed checkpoints, with token
143. The direct-SiLU Python mirror agrees on **61**, differs on **26**, and is
missing **zero** points. First divergence is `pos=0 l=0 ffn_act`, checksum
`e9415b3f` in the mathematical mirror versus `15069f09` in the compiled firmware.
The firmware's existing LUT/interpolation SiLU is not modeled by the mirror's
direct exponential SiLU. The strict trace gate correctly **fails**; it has not
been relaxed and full hybrid bit-exact reference closure is not claimed.

The [compiled FPU trace](v0-tiny-hybrid-fpu-trace.txt) is archived
as an exact baseline for this specific input and implementation. Tiny-image SHA-256:

### SiLU follow-up: reference closure and bounds correction

The independent Python RV32F numerical profile now matches **87/87** archived FPU
checkpoints exactly. The original mathematical mode remains available and still
produces 61 matches / 26 mismatches, confirming that the gate was not loosened.
The discrepancy included fused operations inside the target newlib `expf`, not
just lookup interpolation. A standalone QEMU oracle linked against the same
RV32F libm agreed bit-for-bit for target exp, polynomial SiLU and interpolated SiLU
on a 20,481-point sweep over [-80, 80]. Automated coverage additionally includes
all table nodes/midpoints, deterministic random floats, raw float bit patterns and
adjacent values at branch boundaries. The target-libm identity and scope are in
[the measurement contract](../v0-measurement-contract.md#hybrid-traces).

Boundary testing found a real bounds bug: the greatest FP32 number below 16 rounds
`(x + 16)*128` to 4096, and the old interpolation reads `lut[4097]` past its 4097
elements. The shared firmware helper now returns the endpoint in this case.
An AddressSanitizer/UndefinedBehaviorSanitizer test verifies that no extra element
is read. This correction and the reference additions have **not** been deployed;
the remote board still runs the measured 826f4ae candidate. No performance gain or
new full-SoC run is attributed to this follow-up; the trace comparison is against
the archived compiled run above. Other target transcendental paths and arbitrary
27B inputs are not yet proven bit-exact.

The follow-up passed **125 selected regressions in 38.89 s**
(`build/v0-silu-regressions.log`), including the target-QEMU and sanitizer tests.
Firmware cross-builds passed for both VCU v8 and FK33 v16b, with the existing
unrelated warnings. The local default firmware build was restored to VCU v8.

Remaining V0 work includes physical/useful memory-traffic instrumentation, deeper
state traces as kernels change, filled-context/per-token latency workloads, and
the full clock/constraint audit. The portable-integration and acceleration phases
of the roadmap remain to implement.
